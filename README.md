# Nutrition & Meal Planner

A personalised meal planning app built with Streamlit. It fetches real recipes from the Edamam API, learns your food preferences over time using a content-based ML model, and uses the Groq LLM API to generate recipe summaries, cooking instructions, and a nutrition chat assistant.

## Setup

### Prerequisites
- Python 3.9+
- Edamam Recipe Search API credentials ([developer.edamam.com](https://developer.edamam.com))
- Groq API key ([console.groq.com](https://console.groq.com))

### Install

```bash
pip install -r requirements.txt
```

### Configure

Create a `.env` file in `nutrition-app/`:

```env
EDAMAM_APP_ID=your_app_id
EDAMAM_APP_KEY=your_app_key
EDAMAM_USER_ID=your_registered_email
GROQ_API_KEY=your_groq_key
```

### Run

```bash
streamlit run app.py
```

## ML recommendation model

The ML layer lives in [`services/ml_ranking.py`](services/ml_ranking.py) and is wired into the ranking pipeline in [`services/personalization.py`](services/personalization.py).

### Philosophy

This is **content-based filtering** — no other users' data is involved. The model learns what *you* like by comparing the numerical representation of recipes you've interacted with against candidates. It requires no external ML library beyond NumPy (already pulled in by Plotly).

---

### Step 1 — Feature vector

Every recipe is encoded as a **13-dimensional vector** in [`ml_ranking.py → _feature_vector`](services/ml_ranking.py#L11):

```python
def _feature_vector(recipe: dict, targets: dict) -> np.ndarray:
    features = [
        min(recipe["calories"]   / targets["calories"], 3.0),  # dim 0
        min(recipe["protein"]    / targets["protein"],  3.0),  # dim 1
        min(recipe["carbs"]      / targets["carbs"],    3.0),  # dim 2
        min(recipe["fat"]        / targets["fat"],      3.0),  # dim 3
        min(recipe["total_time"], 120) / 120.0,                # dim 4
        # dims 5–12: binary diet flags
        1.0 if "vegan"        in labels else 0.0,
        1.0 if "vegetarian"   in labels else 0.0,
        1.0 if "keto"         in labels else 0.0,
        1.0 if "paleo"        in labels else 0.0,
        1.0 if "high-protein" in labels else 0.0,
        1.0 if "low-carb"     in labels else 0.0,
        1.0 if "gluten-free"  in labels else 0.0,
        1.0 if "balanced"     in labels else 0.0,
    ]
```

**Nutritional ratios (dims 0–3):** Each macro is divided by *your personal daily target*, which is calculated from your profile via the Mifflin-St Jeor BMR formula in [`personalization.py → calculate_nutrition_targets`](services/personalization.py#L66). Dividing by your target rather than a global constant means the same 500 kcal recipe looks different to a sedentary person vs. a very active one. Values are capped at 3.0 to prevent extreme outliers dominating the direction of the vector.

**Cook time (dim 4):** Normalised to `[0, 1]` over a 0–120 minute range. Recipes over 2 hours all get 1.0.

**Diet flags (dims 5–12):** Binary `1.0 / 0.0` for 8 diet/health categories from the `diet_labels` and `health_labels` fields returned by the Edamam API.

---

### Step 2 — Taste profile

```python
# services/ml_ranking.py:41-53
def build_taste_profile(liked_recipes, targets, disliked_recipes=None):
    if len(liked_recipes) < 3:
        return None          # cold start — fall back to rule-based scoring

    profile = np.mean(
        [_feature_vector(r, targets) for r in liked_recipes], axis=0
    )

    if disliked_recipes:
        dislike_mean = np.mean(
            [_feature_vector(r, targets) for r in disliked_recipes], axis=0
        )
        profile = profile - 0.3 * dislike_mean

    return profile
```

The **taste profile** is the centroid (mean) of all liked recipe vectors. Conceptually it represents "the average recipe you enjoy." The dislike vector is subtracted with a weight of **0.3**, nudging the profile *away* from recipes you've rejected without letting a single dislike dominate.

**Cold start:** fewer than 3 likes returns `None` and the system falls back to the rule-based scorer entirely.

---

### Step 3 — Scoring a candidate recipe

```python
# services/ml_ranking.py:56-58
def ml_score(recipe, taste_profile, targets):
    return _cosine(_feature_vector(recipe, targets), taste_profile)
```

**Cosine similarity** (`_cosine` at [`ml_ranking.py:34`](services/ml_ranking.py#L34)) measures the angle between two vectors, ignoring their magnitudes:

```
similarity = dot(a, b) / (|a| × |b|)
```

A score of **1.0** means the recipe's vector points in exactly the same direction as your taste profile — perfect match. **0.0** means orthogonal — no shared characteristics. Negative values are not possible here because all feature dimensions are ≥ 0.

---

### Step 4 — Blending ML with rule-based scoring

The rule-based scorer [`personalization.py → score_recipe`](services/personalization.py#L97) awards bonus points for:
- Diet label overlap with your preferences (+0.3)
- Cook time within your stated limit (+0.1–0.2)
- Calorie range matching your goal (+0.1–0.2)
- Repeat diet categories from cooking history (+0.1 per cook, capped at 3)

It anchors early recommendations before enough likes exist and never fully disappears.

```python
# services/personalization.py → rank_recipes
ml_weight = min(0.4 + (len(liked) - 3) * 0.05, 0.8)

combined = ml_weight * ml_score(r, taste_profile, targets) \
         + (1 - ml_weight) * rule_score(r, profile) / 2.0
```

The ML weight **starts at 40%** with 3 likes and grows by 5% per additional like, capping at **80%**:

| Likes | ML weight | Rule weight |
|---|---|---|
| < 3 | 0% (cold start) | 100% |
| 3 | 40% | 60% |
| 11 | 80% | 20% |
| 20+ | 80% (capped) | 20% |

---

### Step 5 — Best Pick selection

The "⭐ Best Picks" row uses a separate scorer [`personalization.py → best_pick_score`](services/personalization.py#L162) that prioritises hitting your daily nutrition norms over personal taste:

```python
def best_pick_score(recipe, user_profile):
    targets = calculate_nutrition_targets(user_profile)
    per_meal = {k: max(v / 3, 1) for k, v in targets.items()}

    def closeness(actual, target):
        return max(0.0, 1.0 - abs(actual - target) / target)

    nutrition = (
        closeness(recipe["calories"], per_meal["calories"]) * 0.4 +
        closeness(recipe["protein"],  per_meal["protein"])  * 0.2 +
        closeness(recipe["carbs"],    per_meal["carbs"])    * 0.2 +
        closeness(recipe["fat"],      per_meal["fat"])      * 0.2
    )
    pref = min(recipe.get("_score", 1.0) / 2.0, 1.0)

    return 0.6 * nutrition + 0.4 * pref
```

`closeness` returns 1.0 for a perfect per-meal target match and decreases linearly as the recipe deviates. Calories have twice the weight of individual macros because they're the primary dietary constraint.

### Dislike as a negative signal

When you press 👎 on a recipe ([`recipe_card.py:282`](components/recipe_card.py#L282)):

1. The recipe is saved to `db.json["dislikes"]` via `personalization.py → dislike_recipe`.
2. It is immediately filtered out of all meal rows.
3. On the next page load `build_taste_profile` subtracts `0.3 × mean(disliked_vectors)` from your taste profile, pushing future recommendations away from those recipe characteristics.

---

### Full data flow summary

```
User likes / dislikes recipes
        ↓
personalization.py → get_liked_recipes(), get_disliked_recipes()
        ↓
ml_ranking.py → build_taste_profile(liked, targets, disliked)
        ↓  returns None if < 3 likes (cold start)
personalization.py → rank_recipes()
        ↓  blends ml_score + rule_score with adaptive weight
2_meal_plan.py → _window(ranked, page)
        ↓  slices 8 cards from the 40-recipe pool
meal_row.py → renders scrollable card row
```

## LLM integration

All Groq calls are in [`services/groq_chain.py`](services/groq_chain.py). The client is initialised lazily and cached in a module-level variable so only one connection is made per process ([`groq_chain.py:8-22`](services/groq_chain.py#L8)).

Model used throughout: **`llama-3.1-8b-instant`** — fast inference and sufficient for short-form generation tasks.

---

### 1. Recipe card summaries

**Function:** [`groq_chain.py → generate_recipe_summary`](services/groq_chain.py#L25)

Generates a single enticing sentence (≤15 words) shown under the recipe name on every card. The result is cached in `st.session_state["recipe_summaries"]` after first generation so the API is called only **once per recipe per session**.

```python
prompt = (
    f"Write a single enticing sentence (max 15 words) describing this recipe: "
    f"{recipe_name}. Diet: {diet}. Calories: {calories}."
)
# model: llama-3.1-8b-instant  |  max_tokens: 40  |  temperature: 0.7
```

Falls back to `"A delicious {name} recipe."` silently if the key is missing or the call fails.

---

### 2. Cooking instructions

**Function:** [`groq_chain.py → summarize_instructions`](services/groq_chain.py#L62)

Called inside the recipe Details modal when Edamam does not provide instructions. The prompt explicitly requests steps only, preventing the model from re-listing ingredients:

```python
prompt = (
    f"Write ONLY the cooking steps (4-6 numbered steps) for: {recipe_name}.\n"
    f"Ingredients available: {ingredients_text}\n"
    f"Do NOT list the ingredients again. Start directly with step 1. Be concise."
)
# model: llama-3.1-8b-instant  |  max_tokens: 300  |  temperature: 0.5
```

Lower temperature (0.5) keeps the steps practical and reproducible.

---

### 3. Nutrition chat assistant

**Function:** [`groq_chain.py → build_chat_chain`](services/groq_chain.py#L86)

Returns a stateless `chat(history, message) → str` callable. A system prompt is constructed once per page load and contains:

- Full user profile (age, weight, goal, activity level, dietary preferences, fridge contents)
- Names + AI summaries of the current meal plan recipes (up to 12)

```python
system_prompt = f"""You are a friendly nutrition and meal planning assistant.
User profile: age {age}, weight {weight}kg, goal: {goal} ...
Current meal plan: {recipes_context}
"""
```

Each call sends the last **10 conversation turns** to maintain context without unbounded prompt growth:

```python
messages = [{"role": "system", "content": system_prompt}]
for turn in history[-10:]:
    messages.append({"role": turn["role"], "content": turn["content"]})
messages.append({"role": "user", "content": user_message})
# model: llama-3.1-8b-instant  |  max_tokens: 400  |  temperature: 0.7
```

The assistant is instructed to redirect off-topic queries back to food and nutrition.

## Data sources

| Source | What it provides |
|---|---|
| [Edamam Recipe Search API v2](https://developer.edamam.com/edamam-recipe-api) | Recipe name, image, URL, ingredient lines, diet/health labels, total nutrients, servings |
| Groq / Llama 3.1 8B Instant | Recipe summaries, cooking instructions, chat responses |
| `profile.json` | User profile (age, weight, goal, fridge ingredients, preferences) — local file |
| `db.json` | Likes, dislikes, cooking history — local file |

Nutrition values (calories, protein, carbs, fat) come from Edamam's `totalNutrients` field and are divided by `yield` (servings) to give per-serving figures ([`edamam.py → _parse_hit`](services/edamam.py#L98)).

Without Edamam keys the app runs on 60 built-in mock recipes with realistic nutrition data. Without the Groq key, summaries fall back to a plain description and chat is disabled — neither causes a crash.
